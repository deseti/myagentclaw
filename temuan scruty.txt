Verdict tahap 2

Dan yes:

claim lu soal

• FREE = shared runtime
• STARTER/GROWTH = dedicated runtime
itu didukung code

Tapi gue juga nemu beberapa red flag yang harus lu seriusin.

───

Temuan penting yang udah kebukti

1. Dedicated runtime tier memang real

Di runtime-manager.js ada:

• isDedicatedTier(subTier)
• yang nganggap:
  • STARTER
  • GROWTH
  • PRO
sebagai dedicated

Jadi ini valid:

• FREE shared
• paid dedicated

Ini bagus.

───

2. Tapi dedicated gateway token lu sekarang shared/global

Ini bahaya.

Gue nemu:

const DEDICATED_GATEWAY_TOKEN =
  process.env.OPENCLAW_GATEWAY_TOKEN ||
  process.env.INTERNAL_SECRET_KEY ||
  'myagentclaw-dedicated-gateway-token';

Artinya:

semua dedicated runtime bisa jadi pakai:

• token gateway yang sama
• atau fallback ke INTERNAL_SECRET_KEY
• atau parahnya fallback ke string statis default

Kenapa ini bahaya?

Kalau satu token bocor:

blast radius bisa nyebar ke banyak dedicated runtime

Padahal dedicated runtime harusnya:

• token per runtime
• bukan satu token sakti global

Ini menurut gue red flag serius.

───

3. Ada --allow-unconfigured saat spawn gateway

Gue nemu runtime spawn pakai:

node dist/index.js gateway --bind lan --port 18789 --allow-unconfigured

Ini bahaya kalau dibawa ke production

Karena --allow-unconfigured itu basically bypass startup guard.

Kalau buat bootstrap/dev, oke.
Kalau buat runtime tenant production:

gue anggap ini nggak ideal dan risk tinggi

Kenapa?

• config invalid bisa tetap naik
• startup safety dilewatin
• misconfig jadi lebih gampang lolos

───

4. INTERNAL_SECRET_KEY dipakai terlalu luas

Sekarang INTERNAL_SECRET_KEY dipakai buat:

• internal routes auth
• fallback dedicated gateway token
• kemungkinan trust antar komponen

Problem:

satu secret dipakai terlalu banyak fungsi.

Kalau bocor:

• internal backend routes kebuka
• gateway auth bisa ikut kena
• trust boundary antar komponen collapse

Ini anti-pattern.

Harusnya dipisah:

• internal API secret
• gateway token
• service-to-service auth
• runtime-specific token

───

5. Internal auth masih bisa lewat query param

Lu masih punya logic:

• x-internal-key
• atau request.query.internal_key

Ini jelek banget buat production

Karena query param bisa:

• ke-log di reverse proxy
• ke-log di access log
• bocor di monitoring / analytics / history
• lebih gampang keseret ke tempat yang nggak harusnya

Ini harusnya dihapus.

Internal auth jangan pernah lewat query param kalau bisa dihindari.

───

6. Free shared runtime memang masih risk surface besar

Karena ada:

• MYAGENTCLAW_ENABLE_SHARED_WORKSPACE=1

Jadi free tier memang shared.

Itu acceptable, asal:

• capability dibatasi keras
• fs sempit
• exec sempit
• no elevated
• per-tenant quotas jalan
• abuse handling bagus

Kalau nggak, free tier jadi tempat abuse paling gampang.

───

7. Dedicated runtime belum otomatis berarti isolated secrets

Dari yang gue lihat sekarang,
gue belum dapat bukti kuat bahwa setiap dedicated runtime punya:

• gateway token unik per tenant
• internal secret unik per tenant
• env terpisah yang benar-benar granular

Yang kebaca justru:

ada kecenderungan secret global dipakai ulang

Ini bikin:

• runtime dedicated secara proses, tapi
• trust secret-nya belum dedicated penuh

Itu artinya isolasi lu bagus di compute,

tapi belum cukup bagus di auth plane.

───

Jadi apa yang beneran berbahaya?

Bahaya 1 — shared/fallback gateway token

Ini menurut gue critical



karena ngerusak isolation story yang harusnya jadi keunggulan tier paid.

Bahaya 2 — --allow-unconfigured di runtime tenant

Ini high risk
buat production.

Bahaya 3 — internal key via query param

Ini medium-high
dan harus dibersihin.

Bahaya 4 — satu INTERNAL_SECRET_KEY untuk banyak boundary

Ini high
karena blast radius besar kalau bocor.


Bahaya 5 — free tier shared runtime kalau capability terlalu luas

Ini conditional high
tergantung policy actual di OpenClaw config tenant free.

───

Jadi apakah arsitektur lu bagus?

Iya.

Tapi sekarang jawaban profesional gue:

arsitektur lu bagus di level shape

tapi ada beberapa security implementation choices yang bisa ngerusak kekuatan desain itu sendiri.

Alias:

• desain makro: bagus
• beberapa detail keamanan: masih bahaya

───

Kalau gue jadi auditor keamanan, prioritas fix gue:

Prioritas 1

token dedicated runtime harus unik per runtime/tenant

Jangan fallback ke:

• OPENCLAW_GATEWAY_TOKEN global
• INTERNAL_SECRET_KEY
• apalagi default literal string

Harus:

• generate token unik per runtime
• simpan terpisah
• rotate-able

───

Prioritas 2

hapus --allow-unconfigured dari runtime tenant production

Simpan cuma untuk dev/bootstrap.

───

Prioritas 3

pisahkan secret berdasarkan fungsi

Bikin terpisah:

• internal API auth
• gateway token
• runtime control token
• webhook secrets
• JWT secret
• tenant-scoped secrets kalau perlu

───

Prioritas 4

matikan auth via query param

Paksa header only.

───

Prioritas 5

dokumentasikan capability policy per tier

Khusus FREE:

• no elevated
• exec ketat
• fs ketat
• quotas/rate limit keras
